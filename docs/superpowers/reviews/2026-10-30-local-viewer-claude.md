# Codex 제안 검토: ctx-kit 기록 뷰어

> **검토 범위**: 제공된 제안문만 검토했습니다. ctx-kit의 저장소, 데이터 스키마, 훅, 보관(archive) 로직은 확인하지 않았습니다. 아래에서 "현재 구조"를 언급한 부분은 제안문에 적힌 내용을 전제로 한 추정입니다. 실제 구현과 맞는지는 계획의 0단계에서 확인해야 합니다.

## 판정

만들 가치가 있다는 판단과 "정적 HTML 먼저, 원본은 Markdown·JSONL 유지"라는 방향에는 동의합니다. 다만 첫 버전에 화면 네 개와 Git 연동, 결정 기록까지 담은 것은 과합니다. 커밋 연결 방법, 사실의 출처 표시, HTML 삽입 보안이 아직 구체적이지 않습니다. 첫 버전은 **현황 + 통합 타임라인 + 파일별 작업 기록**으로 줄이고, 이 위험 요소들을 데이터 모델 단계에서 먼저 해결하는 것을 권장합니다.

## 우선순위별 문제점

### P0: 구현 전에 반드시 정해야 할 것

**1. 커밋 연결 방법이 정해지지 않았습니다.**
제안은 "파일 → 작업 기록 → 커밋"을 이어서 보여 주자고 하면서, 훅이 커밋 *전에* pending 기록을 남긴다고 적었습니다. 그렇다면 기록과 커밋을 이어 줄 확실한 키가 없을 수 있습니다. 시각이나 파일 목록이 비슷한 커밋을 골라 연결하는 추정 방식은 틀린 정보를 사실처럼 보여 줍니다.
- 연결은 **기록에 커밋 해시가 명시된 경우에만** 합니다.
- 해시가 없으면 "커밋 미확인"으로 표시합니다.
- 해시가 있어도 Git에서 찾을 수 없으면(amend나 rebase로 사라진 경우) "히스토리에 없음"으로 표시합니다.

**2. HTML에 데이터를 넣을 때의 보안이 빠져 있습니다.**
로그, 커밋 메시지, 브랜치 이름, 파일 경로는 모두 신뢰할 수 없는 문자열입니다. `</script>`나 `javascript:` 링크, 외부 이미지가 들어 있으면 HTML을 여는 순간 스크립트가 실행되거나 외부로 요청이 나갈 수 있습니다. 대응 방법은 5절에 정리했습니다.

**3. 출처 구분을 표시 단계가 아니라 데이터 모델 단계에서 해야 합니다.**
제안의 정확성 원칙은 옳지만, 화면을 만들 때 신경 쓰는 정도로는 지켜지지 않습니다. 모든 표시 항목이 다음 세 출처 중 하나를 필드로 가져야 합니다.
- **문서 기재**: 컨텍스트 문서에 적힌 내용
- **기록 당시 로그**: 작업 로그에 남은 당시의 기록
- **Git 조회**: 생성 시점에 Git에서 직접 조회한 값

### P1: 범위와 구조

**4. 결정 기록은 원본 데이터가 있는지 불확실합니다.**
"대안"이나 "폐기된 결정"이 구조화된 데이터로 남아 있지 않다면, 이를 화면에 보여 주려면 문서를 해석해야 합니다. 그러면 사실상 AI 요약이나 휴리스틱이 필요해져 제안 스스로 세운 원칙과 충돌합니다.

**5. file:// 제약이 고려되지 않았습니다.**
Chrome 등에서는 file://로 연 페이지가 옆 경로의 JSON을 `fetch`로 읽거나 ES 모듈을 불러오는 것이 막힙니다. 따라서 데이터와 코드를 **모두 HTML 한 파일 안에 넣어야** 합니다. 이 경우 이력이 길어질수록 파일 크기가 직접 커집니다.

**6. 보관 중 읽기와 중복 기록 문제가 언급되지 않았습니다.**
최근 기록과 보관 기록을 합쳐 보여 주려면, 보관 작업 도중에 읽거나 같은 작업에 pending 기록과 최종 기록이 둘 다 있을 때 어떻게 처리할지 정해야 합니다(4절).

### P2: 운영과 평가

**7. 갱신 시점과 오래된 화면 경고가 없습니다.** 정적 HTML은 항상 과거의 스냅숏입니다.

**8. "1분 안에 파악" 목표를 어떻게 측정할지 정의되지 않았습니다.**

## 2. 정적 HTML 검토

**장점**
- 서버를 띄우거나 종료할 필요가 없고, 접근 범위를 관리할 필요도 없습니다.
- 오프라인에서 열리고, 파일 하나라서 다루기 쉽습니다.
- 생성 결과를 다시 만들 수 있어 원본 데이터가 늘어나지 않습니다.

**단점과 대응**

- **file:// 제약**
  - 데이터는 `<script type="application/json">` 블록에 넣고 `JSON.parse`로 읽습니다.
  - CSS와 JS는 모두 인라인으로 넣고 CDN은 쓰지 않습니다.
  - file://에서 `localStorage`의 동작은 브라우저마다 다르므로 상태 저장에 의존하지 않습니다.
  - 선택한 필터, 검색어, 선택한 항목은 URL 해시(`#file=...&q=...`)에 저장합니다. 해시는 file://에서도 동작하고, 해당 화면을 북마크할 수도 있습니다.

- **갱신 시점**
  - 커밋 훅에서 자동으로 다시 생성하는 방식은 보류합니다. 커밋을 느리게 만들고 실패 지점을 늘립니다.
  - 명시적인 명령 하나로 "생성 후 브라우저 열기"를 하도록 합니다.
  - 화면 상단에 생성 시각과 경과 시간을 표시하고, 일정 시간이 지나면 "다시 생성하세요" 안내를 띄웁니다. 경과 시간은 JS로 계산할 수 있지만, file://에서 최신 Git 상태와 비교하는 것은 불가능하다는 점을 전제로 합니다.

- **긴 이력**
  - 수천 건까지는 전부 넣고 메모리에서 검색해도 충분하다고 예상합니다.
  - 그보다 많으면 보관 기록은 요약 필드만 넣고 본문은 잘라 내는 방식을 고려합니다. 또는 기간 옵션으로 범위를 제한합니다.
  - 정확한 기준은 생성 시간, 파일 크기, 검색 지연을 측정해서 정합니다.

- **검색 UX**
  - 검색창은 하나로 두고 필터(유형, 기간, 파일)와 함께 씁니다.
  - 대소문자를 구분하지 않고, 일치 부분을 강조합니다.
  - 결과 개수를 표시하고, 키보드로 포커스를 이동할 수 있게 합니다.
  - 한글은 **유니코드 정규화(NFC)**를 꼭 적용합니다. macOS 파일 경로는 NFD로 저장되는 경우가 있어, 정규화하지 않으면 파일 경로 검색이 실패할 수 있습니다.

## 3. 가벼운 배포 구성 (현재 코드를 확인하지 않았다는 전제)

**원칙**
- 새 런타임 의존성을 추가하지 않습니다. npm, 빌드 도구, 템플릿 엔진, Markdown 라이브러리를 쓰지 않습니다.
- Python을 이미 사용 중이라면 **표준 라이브러리만으로** 생성기를 만듭니다. Python이 필수가 아닌 환경이라면, 이 기능만 "Python 필요" 안내와 함께 비활성화합니다.
- Bash 쪽은 하위 명령으로 생성기를 호출하는 역할만 합니다.
- HTML 템플릿은 CSS와 JS를 포함한 파일 하나로 배포물에 넣습니다.
- Markdown 렌더링은 제목, 목록, 코드 블록, 링크 정도의 작은 하위 집합만 지원합니다. 원본 문서 안의 HTML은 해석하지 않고 텍스트로 보여 줍니다.

**구조**
1. **읽기와 정규화 계층**: 문서, 최근 로그, 보관 로그, Git 결과를 하나의 중간 JSON으로 합칩니다. 이 단계에서 출처 표시, 중복 제거, 오류 처리를 끝냅니다.
2. **렌더러**: 중간 JSON을 템플릿에 넣기만 합니다. 데이터를 해석하지 않습니다.
3. 중간 JSON을 별도로 출력하는 옵션을 둡니다. 이 출력을 기준으로 테스트하고, 나중에 로컬 웹 뷰어를 만들 때도 같은 데이터를 재사용합니다.

**0단계에서 확인할 것**
- 지원하는 Python 버전
- JSONL 레코드의 필드와 스키마 버전
- 보관 방식(이동인지 복사인지, 압축 여부, 잠금 사용 여부)
- pending 기록이 나중에 해시로 갱신되는지 여부
- 결정 기록이 존재하는지와 그 형식
- 기본 출력 위치와 `.gitignore` 처리

## 4. 사실 구분과 데이터 일관성 점검 항목

**출처와 시점**
- 모든 항목에 출처(문서/로그/Git)와 시각을 붙입니다.
- 로그에 남은 "테스트 통과"는 "기록 당시 통과로 기록됨"으로 표시합니다. 현재 테스트 상태처럼 보이지 않게 합니다.
- 문서가 오래됐는지는 "이 문서가 마지막으로 수정된 커밋 이후 N개의 커밋이 있음"처럼 **Git에서 측정할 수 있는 사실**로만 경고합니다. 내용이 맞는지는 판단하지 않습니다.
- Git이 설치되지 않았거나 Git 저장소가 아니거나 조회가 실패하면, Git 영역만 "조회 불가"로 표시하고 나머지 화면은 그대로 동작해야 합니다.

**잘못되거나 오래된 기록**
- 로그의 파일 경로가 지금은 존재하지 않으면 "현재 없음"으로 표시합니다. 이름 변경 추적(`--follow`)은 보류합니다.
- 알 수 없는 유형이나 스키마 버전, 필수 필드가 빠진 레코드는 버리지 말고 "해석 불가" 항목으로 보여 주고 개수를 집계합니다.
- 시간대가 섞여 있으면 정렬이 어긋납니다. 저장된 시간대 형식을 확인합니다.

**중복**
- 레코드에 고유 id가 있는지 확인합니다. 없으면 (시각, 유형, 내용) 해시를 중복 판별 키로 씁니다.
- pending 기록과 최종 기록이 함께 있을 때의 정책을 정합니다. 권장안은 둘을 하나로 묶고, 상태가 바뀐 이력을 함께 보여 주는 것입니다.

**보관 중 읽기**
- 보관이 "최근 기록에서 지우고 보관 기록에 추가하는" 이동 방식이라면, 그 사이에 읽을 때 기록이 누락되거나 중복될 수 있습니다.
- 대응은 두 가지입니다.
  - 기존 잠금이 있으면 같은 잠금을 공유해서 읽습니다.
  - 잠금이 없으면 보관 기록을 먼저 읽고 최근 기록을 나중에 읽은 뒤 중복을 제거합니다. 이렇게 하면 누락을 피하고 중복은 제거 단계에서 처리할 수 있습니다.
- 마지막 줄이 쓰다 만 상태(잘린 JSONL)이면 그 줄만 건너뛰고 경고합니다.

## 5. 오프라인 HTML 최소 보호

1. **스크립트 문자열**
   - JSON 블록에 넣기 전에 `<`, `>`, `&`, U+2028, U+2029를 `\uXXXX` 형태로 이스케이프합니다. 이렇게 하면 데이터 안의 `</script>`가 스크립트 블록을 닫지 못합니다.
   - 데이터를 `eval`이나 `Function`으로 실행하지 않습니다.
2. **HTML 삽입**
   - 데이터는 `textContent`나 DOM 생성 API로만 넣습니다. 데이터를 `innerHTML`에 넣지 않습니다.
   - Markdown은 먼저 전체를 이스케이프한 뒤, 허용한 구문만 태그로 바꿉니다.
3. **URL**
   - `http`, `https`, 문서 내부 앵커(`#`)만 허용합니다. `javascript:`, `data:`, `vbscript:`, `file:`은 링크로 만들지 않고 텍스트로 보여 줍니다.
   - 외부 링크에는 `rel="noopener noreferrer"`를 붙입니다.
4. **외부 이미지**
   - 불러오지 않습니다. 열람 추적과 오프라인 위반을 막기 위해서입니다. 대신 링크 텍스트로 보여 줍니다.
5. **CSP 메타 태그**
   - 기본값은 `default-src 'none'`으로 막고, `connect-src 'none'`, `img-src data:`, `base-uri 'none'`, `form-action 'none'`을 지정합니다.
   - 인라인 스크립트는 가능하면 해시로 허용합니다.
   - 이렇게 하면 렌더링 단계에서 버그가 생겨도 외부로 데이터가 나가는 것을 한 번 더 막을 수 있습니다.
6. **Git 호출**
   - 셸을 거치지 않고 인자 배열로 실행합니다. 경로 앞에는 `--`를 붙입니다.
7. **출력 파일 보존**
   - 같은 디렉터리의 임시 파일에 먼저 쓰고, 다 쓴 뒤 원자적으로 이름을 바꿉니다.
   - 대상 경로가 심볼릭 링크이거나, 이 도구가 만든 파일임을 나타내는 표식이 없는 기존 파일이면 덮어쓰지 않고 거부합니다. `--force`를 준 경우만 예외로 합니다.
   - 기본 출력 위치는 프로젝트 안의 고정 경로로 정하고 `.gitignore`에 추가합니다.
8. **민감 정보**
   - 로그에 토큰이나 개인 경로가 들어 있을 수 있습니다. HTML은 공유하기 쉬운 형태이므로 생성 시 "공유 주의" 안내를 표시합니다. 자동 마스킹은 보류합니다.

## 6. 완료 기준과 검증 시나리오

### 완료 기준
- 명령 하나로 HTML 파일 하나가 생성됩니다.
- Chrome, Firefox, Safari에서 file://로 열었을 때 **네트워크 요청이 0건**입니다(개발자 도구로 확인).
- 첫 화면에 현재 상태, 다음 행동, 생성 시각, Git 스냅숏 라벨이 보입니다.
- pending 기록이 "커밋됨"으로 표시되는 경우가 없습니다.
- 테스트 결과에는 모두 "기록 당시" 라벨이 붙어 있습니다.
- 최근 기록과 보관 기록을 합친 검색과 파일별 조회가 동작합니다.
- 입력이 같으면 출력이 같습니다. 생성 시각만 예외입니다.
- 새 런타임 의존성이 추가되지 않았습니다.
- 손상된 레코드가 있어도 생성이 중단되지 않습니다.

### 검증 시나리오
1. 로그가 없는 새 프로젝트: 빈 상태 안내가 나옵니다.
2. 해시 없는 pending 기록: "커밋 미확인"으로 나옵니다.
3. amend로 사라진 커밋 해시: "히스토리에 없음"으로 나옵니다.
4. 문서가 마지막으로 수정된 뒤 커밋이 여러 개 쌓인 경우: 문서 노후 경고가 나옵니다.
5. 공격 문자열 테스트 데이터(`</script><script>`, `<img onerror>`, `[x](javascript:...)`, 외부 이미지, U+2028): 아무것도 실행되지 않고, 요청이 나가지 않으며, 문자열이 그대로 보입니다.
6. 같은 기록이 최근 기록과 보관 기록 양쪽에 있는 경우, 그리고 보관 작업 중에 생성한 경우: 누락과 중복이 없습니다.
7. 마지막 줄이 잘린 JSONL: 경고가 나오고 나머지 기록은 정상적으로 보입니다.
8. 기록 5천 건과 2만 건: 생성 시간, 파일 크기, 검색 응답 시간(목표 약 100ms)을 기록합니다.
9. 출력 경로가 심볼릭 링크이거나 사용자가 만든 파일인 경우: 덮어쓰기를 거부합니다.
10. Git이 없는 디렉터리: Git 영역만 "조회 불가"로 나옵니다.
11. 삭제된 파일 경로, NFD로 저장된 한글 파일명: 표시와 검색이 모두 정상입니다.
12. **1분 목표**: 며칠 쉰 뒤 프로젝트를 열어 현재 상태와 다음 행동을 말로 설명하는 데 걸리는 시간을 직접 잽니다. 기존처럼 Markdown 파일을 직접 읽었을 때와 비교합니다.
